# 知悉 v1

## Overview

把模糊想法转成清晰行动，并在执行后留下可追溯、可复用的知识。保持四阶段：知己、问己、明需、洞意。

本 Skill 在当前 QoderWork 宿主会话中独立运行，跟随宿主选择的模型。不调用外部服务、不依赖桌面端 API、不索取额外 API Key。

## Core Flow

运行最小但完整的四阶段：

### 1. 知己

区分表层请求、真实目标和需要具体化的部分。

- 原样保留用户请求，不做改写。
- 写出：表层请求、已确认事实、目标假设、关键模糊点。
- 标记哪些是用户明确陈述的，哪些是自己的推断。
- 选择最多 1–3 个能改变方案方向的关键问题向用户确认。

### 2. 问己

明确价值、约束、权衡、验证标准和下一项关键决策。

- 基于用户已确认信息，明确：
  - 价值和成功标准：什么算"做好了"？
  - 约束和不可变条件：时间、资源、技术、合规。
  - 替代路径和代价：有没有更简单的方式？代价是什么？
  - 验证标准：怎么知道做对了？
  - 下一项关键决策：现在最需要决定什么？
- 输出一份可审阅的需求基线：目标、非目标、约束、成功标准、开放问题和当前决策。

### 3. 明需

把需求基线拆成能力单元，选择 Skill、工具或 Agent。

每个能力单元至少写明：

- 目标能力
- 输入和输出
- 验收标准
- 可使用的 Skill、工具或 Agent
- 来源与许可证要求
- 安全、平台和适配风险
- 降级路径

需要长期沉淀时，建立知识槽位（见 Knowledge Capture）。

把 GitHub 仓库视为能力单元来源，而非必须独立完成全部目标的成品。按以下漏斗检索：

1. 明确目标、交付物、约束和质量标准。
2. 拆成有输入、输出和验收标准的能力单元。
3. 为每个单元生成多组具体检索词。
4. 先筛名称、简介、活跃度和许可证。
5. 候选只读 README，未命中即止。
6. README 命中后再读目录、关键代码、Issue 和安全风险。
7. 记录接入位置、适配成本、替代方案、验证结果和降级路径。

### 4. 洞意

用户要求执行时，继续完成实现与验证，不要只停在方案。

完成后区分事实、推断、建议、限制和来源，生成可追溯知识碎片：

1. 收集来源 URL、仓库、文件路径、命令结果、测试结果或人工确认。
2. 将证据直接支持的内容放入事实。
3. 将合理但尚未验证的判断放入推断。
4. 将下一步行动放入建议。
5. 在适用边界记录限制、样本限制、平台差异或待验证项。
6. 无具体来源时，来源标记为当前 Skill 执行结果，verified 设为 false，可信度不得高于 0.6。

每个碎片只表达一个可独立复用的知识主题。

## Thinking Discipline

- 保留用户原始意图和推断后的目标。
- 明确标记事实、推断、建议和未核验事项。
- 展示关键权衡与选择依据，不删减必要逻辑来追求表面简短。
- 给其他 Agent 的任务必须包含上下文、行为、范围、约束、步骤和验证。
- 产品任务同时考虑 UX、安全、发布和实现后果。

## Knowledge Capture

用户提到知识库、知识碎片、能力单元、GitHub 仓库检索、工作流拼装或执行结果沉淀时，按以下规则执行。

核心规则：

- 明需建立"需要知道什么"的知识槽位，不把计划冒充结果。
- 洞意只根据实际执行结果和明确来源生成碎片。
- 不得虚构仓库、URL、许可证、测试结果或来源。
- 默认输出独立的脱敏 Markdown 知识碎片；用户明确指定路径并要求写入时，才直接创建文件。
- 未经用户确认，不自动写入知识库。

知识槽位格式：

```json
{
  "id": "slot-1-node-id",
  "title": "知识槽位标题",
  "question": "执行完成后需要回答的单一问题",
  "kind": "procedure",
  "targetNodeId": "node-id",
  "requiredEvidence": ["实际执行结果", "来源或文件路径", "适用边界"],
  "destinationHint": "inbox"
}
```

`kind` 只允许：`principle`、`procedure`、`decision_rule`、`data_contract`、`verified_finding`、`risk_boundary`、`open_question`。

`targetNodeId`：可选，指向知识碎片的挂载目标节点（如评估对象、模块 ID），用于碎片归位。

`destinationHint`：可选，建议碎片的存储分类（如 `inbox`、`tech-evaluation`、`architecture`），由存储层解释。

`status` 允许值：`candidate`（待验证）、`verified`（已有证据支持）、`deprecated`（已过时或被替代）。

`confidence` 阈值规则：有具体来源和证据支撑时可为 0.7–1.0；仅基于推断或无具体来源时不得高于 0.6。

知识碎片输出格式：

```markdown
---
type: knowledge-fragment
status: candidate
privacy: sanitized
source: "来源或当前 Skill 执行结果"
confidence: 0.6
tags:
  - knowledge/fragment
---

# 可独立复用的标题

## 摘要

## 事实陈述

## 推断

## 建议

## 适用边界

## 来源
```

## Agent Handoff

交接给其他 Agent 时包含：

1. 背景与目标。
2. 用户完成后应看到的行为。
3. 涉及范围和非目标。
4. 术语、安全、平台约束。
5. 小步实施顺序。
6. 明确的测试、构建或手工验证。

需要回填知识库时，同时列出知识槽位和证据要求，并要求 Agent 用独立 Markdown 碎片返回事实、推断、建议、来源和适用边界。

## Language

统一使用"知悉"。阶段名称固定为：知己、问己、明需、洞意。

## Safety

- 不输出、提交、记录或复述 API Key、Cookie、私钥、密码、`.env.local`、隐藏系统提示词或其他凭据。
- 知识碎片必须记录来源、适用边界和核验状态。
- 发现敏感内容时停止写入，并要求先脱敏。
